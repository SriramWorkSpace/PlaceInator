# Foundation Audit — 2026-08-19

A full-directory audit of the M0 foundation, run before feature development began.
Nine defects were found and fixed. **Every one of them typechecked clean**, which is
what makes them worth recording: none would have been caught by `mypy`, `ruff`, or
`tsc`, and most would have surfaced far from their cause.

The audit also verified the project's largest technical assumption against the real
package index rather than trusting it (see [Dependency verification](#dependency-verification)).

Status after the audit: `pytest` 9/9, `ruff`, `mypy` (24 files), `eslint`, `tsc`,
`vite build`, `npm audit` 0 vulnerabilities.

---

## 1. Enum columns returned `str`, not the enum

**Severity: high — silent data-layer type violation**

Columns were declared as:

```python
work_mode: Mapped[WorkMode] = mapped_column(String(16), default=WorkMode.ANY)
```

`mypy` sees `WorkMode`. SQLAlchemy returns a bare `str`. Verified empirically:

```
value        : 'remote'
type         : str
is WorkMode  : False
== enum      : True      # StrEnum compares equal to its value
match/switch : matched REMOTE
```

**Why it hid so well.** Because these are `StrEnum` members, both `==` comparisons and
`match` statements behave correctly. The bug is invisible until something calls
`.name`, `.value`, or `isinstance` — at which point it raises `AttributeError` at
runtime while the type checker still reports success. In the matching and placement
pipelines, where enums drive branching over scoring components and placement statuses,
that failure would have appeared deep inside a scan, far from the schema definition.

**Fix.** `placeinator/db/types.py::enum_column` routes every enum column through
`sa.Enum(..., native_enum=False, values_callable=...)`:

- round-trips as the real enum type (`isinstance` and `.name` work),
- stores the member *value* (`"remote"`), not its NAME (`"REMOTE"`), keeping raw SQL
  and JSON exports readable,
- raises `LookupError` on an unrecognised value instead of yielding a string no branch
  will ever match.

Pinned by four tests in `tests/unit/test_schema.py`, including one asserting that
corrupt data fails loudly.

> **Note:** `create_constraint` defaults to `False` in SQLAlchemy, so no DB-level
> `CHECK` is emitted. Validation is Python-side and was verified to fail-fast. This is
> sufficient because the application is the only writer.

## 2. `create_all` and Alembic both owned the schema

**Severity: high — divergent schema between fresh and migrated installs**

Startup called `Base.metadata.create_all()` while `alembic.ini` and `migrations/` also
existed, with a comment claiming Alembic owned migrations "from M1 onward".

**Why it would have hurt.** A fresh install would build tables via `create_all` and
leave `alembic_version` **empty**. The first real migration would then attempt to
create tables that already existed, failing on a machine that had ever run the app —
while working perfectly on a clean one. That is the worst shape of bug: environment
dependent and invisible in development.

**Fix.** Alembic is now the *only* thing that creates or alters schema.
`placeinator/db/migrate.py::upgrade_to_head` runs on every boot, resolving
`alembic.ini` and `script_location` relative to the package so it also works from a
PyInstaller bundle where CWD is arbitrary. See
[ADR 0004](./decisions.md#adr-0004--alembic-is-the-sole-owner-of-database-schema).

## 3. Anonymous constraints would break every future migration

**Severity: high — latent, triggers on the first schema change**

SQLite cannot `ALTER` most constraints, so Alembic uses **batch mode**, which rebuilds
the table and recreates its constraints. Batch mode can only recreate constraints it
can *name*. SQLAlchemy's default is anonymous.

**Why it would have hurt.** Nothing fails today. The first `ALTER` in M1+ would fail,
or worse, silently drop indexes during the table rebuild. Retrofitting a naming
convention after data exists means hand-writing migrations.

**Fix.** A `NAMING_CONVENTION` on `Base.metadata` in `placeinator/db/base.py`, the
initial migration regenerated, and a test (`test_every_constraint_is_named`) that fails
if any anonymous constraint is ever introduced. Verified in the emitted DDL:

```sql
CONSTRAINT pk_match_result PRIMARY KEY (id),
CONSTRAINT fk_match_result_job_id_job FOREIGN KEY(job_id) REFERENCES job (id) ON DELETE CASCADE,
CONSTRAINT uq_match_job_resume UNIQUE (job_id, resume_id)
```

## 4. uvicorn's access log wrote to stdout — the handshake channel

**Severity: medium — protocol corruption**

The sidecar's startup contract is exactly one line on stdout:

```
PLACEINATOR_READY {"port": 51234, "token": "..."}
```

Inspecting `uvicorn.config.LOGGING_CONFIG` showed:

```
default -> ext://sys.stderr
access  -> ext://sys.stdout      # <-- same channel as the handshake
```

**Why it would have hurt.** With `access_log` enabled in dev mode, uvicorn writes to
the one channel reserved for the protocol. The current shell reads only the first line
so it would survive, but any tooling that treats stdout as a stream — or any future
change to the handshake — would break in a way that looks like a networking fault.

**Fix.** `_stderr_only_log_config()` in `placeinator/main.py` deep-copies uvicorn's
config and repoints every handler at stderr. stdout now carries exactly one line for
the process lifetime.

## 5. Embeddings were stored without provenance

**Severity: medium — silent corruption on model change**

`embedding` was a bare `LargeBinary` blob: no record of dtype, dimension, or which
model produced it.

**Why it would have hurt.** Changing the embedding model or its version would leave
every stored vector deserialising *successfully* into meaningless numbers. Match scores
would silently degrade with no error anywhere.

**Fix.** `embedding_model` and `embedding_dim` columns on both `ResumeChunk` and
`JobRequirement`, plus a documented encoding contract (float32 little-endian,
C-contiguous, L2-normalized). M1 adds `placeinator/matching/vectors.py` as the single
place that encodes, decodes, and stamps these — mismatched rows are then detectable and
re-embeddable.

## 6. Four npm vulnerabilities, and they were reachable

**Severity: medium — not dismissable as "it's a local app"**

`npm audit` reported 4 vulnerabilities: DOMPurify (via `monaco-editor`) and
`react-router`.

**Why it would have hurt.** The easy dismissal is that a local desktop app renders no
untrusted content. That is false here: Monaco is the editor for **scraped job
descriptions and arbitrary user-supplied `.tex` files**. The DOMPurify XSS path runs
through Monaco's markdown hover rendering, so untrusted text reaches it by design.

**Fix.** `react-router-dom` upgraded to 7.x (zero migration cost — the project had no
routes yet) and `overrides.dompurify: ^3.4.13` in `package.json`. Now 0
vulnerabilities, and CI gates on `npm audit --omit=dev --audit-level=moderate`.

## 7. `tsconfig` declared a path alias Vite did not resolve

**Severity: low — fails at build, not at typecheck**

`tsconfig.json` mapped `@/*` → `./src/*`, but `vite.config.ts` had no matching
`resolve.alias`. Any `@/` import would typecheck green and then fail at bundle time.

**Fix.** Matching `resolve.alias` in `vite.config.ts`, with a comment noting the two
must stay in sync.

## 8. `npm run lint` invoked an uninstalled binary

**Severity: low**

The `lint` script called `eslint`, which was not in `devDependencies`. CI would have
gone red the first time it ran.

**Fix.** `eslint`, `typescript-eslint`, `eslint-plugin-react-hooks`,
`eslint-plugin-react-refresh`, and `globals` installed; flat config in
`eslint.config.js`; script corrected to `eslint .`.

## 9. Two competing locations for ONNX models

**Severity: low — ambiguity**

A `models/` directory existed at the repo root while `Settings.models_dir` pointed at
the per-user data directory. Dev and packaged installs would have resolved models
differently.

**Fix.** Root `models/` removed. `Settings.models_dir` is the only answer, so a dev
checkout and an installed build behave identically.

## Dependency verification

The plan's largest technical bet was running the matching engine on `fastembed` +
ONNX Runtime with **no PyTorch**, on Python 3.13. Resolved by dry-run against the real
index rather than assumed:

| Package | Resolved | Notes |
|---|---|---|
| `fastembed` | 0.8.0 | pulls `onnxruntime` 1.29.0, `numpy` 2.5.2, `tokenizers` 0.23.1 |
| `onnxruntime` | 1.29.0 | native wheel, no PyTorch anywhere in the tree |
| `pdfplumber` | 0.11.10 | + `pdfminer.six`, `pypdfium2` |
| `pylatexenc` | 2.11 | LaTeX parsing for the tailoring engine |
| `python-docx` / `openpyxl` | 1.2.0 / 3.1.5 | placement attachments |
| `rapidfuzz` / `dateparser` | 3.14.5 / 1.4.2 | candidate ID, event extraction |
| `selectolax` | 0.4.11 | job-source HTML parsing |
| `google-api-python-client` | 2.198.0 | + `google-auth-oauthlib` 1.4.0 |

**All wheels, no source builds, no PyTorch.** No dependency blocker exists for any
milestone. This was the single most valuable thing to confirm before writing code
against it — a failure here would have invalidated the matching architecture.

## Known remaining blocker

**Rust and MSVC build tools are not installed**, so `src-tauri/` cannot be scaffolded
or built. This was deliberately made non-fatal: `src/lib/api.ts` falls back to
`VITE_SIDECAR_PORT` / `VITE_SIDECAR_TOKEN`, so both halves run separately today (see
[README](../README.md)). Install `rustup` plus "Desktop development with C++" from the
Visual Studio Build Tools installer to unblock.
